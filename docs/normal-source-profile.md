# Installed A normal source profile

The optional `[normal_financial_source]` TOML section contains exactly `profile`
(an absolute private JSON path) and `sha256` (that file's actual hash). It is
accepted only with the explicit `two_step_per_key` architecture and actual SDK
pin. Engine construction uses the fixed installed
`simulator.normal_profile.collector_from_profile` factory; profile data cannot
select a module, Python expression, executable plugin or alternative architecture.
An explicit collector and a configured profile together are refused. Without a
profile the existing explicit-dependency behavior remains unchanged, including
its refusal to qualify normal readiness when no collector is installed.

The JSON has exactly these fields: `schema_version`1, `architecture_profile`,
`financial_pins`, `admission_sequence`, `boundary_sha256`, `envelope_sha256`,
`opening_sha256`, `funding_plan_sha256`, `target_epoch_id`,
`capture_configuration`, `target_configuration`, `member_configuration`, `tools`
and `funding_configuration`. The four declaration hashes refer to already
recorded original Store declarations, not proposals. The final financial epoch,
actual deployment registry and configured runtime must match the same pins.
The current driver is independently hashed during construction. No historical
SDK label, inactive qualification binary or web source is inferred to be deployed.

Every boundary member must retain its original `treasury_member_verified` event,
identity, descriptors, genesis and pins. Both reader configurations and capture
configuration must match the admitted static factory. Actor mapping includes
all original twelve and all twelve genuinely predeclared dormant future members;
none is opened, recreated, removed or assumed online. The original funding plan
must retain twelve initial/twelve future clients, the same grant as the envelope,
and its exact principal/batch-fee caps. The profile does not choose a grant or
repair a missing plan.

`tools` contains exactly `policy`, `binding` and `pending`, each with its one
actual executable command, SHA256 and private evidence directory. The original
collector qualification binds those exact commands/files/component hashes and
must explicitly record `proof_schema_versions.pending=2`. The pending proof
must actually return schema2 and the native-derived `anchor_spender_txid` during
each relevant proof. Paths and filenames alone are not qualification. The
currently selected qualified artifacts and receipts must be supplied by the
operator; this source hardcodes no active SDK/tool hash or release promotion.

`funding_configuration` contains an original ownership qualification sequence
and `packages`, keyed by exact declaration SHA256. Each entry has
`declaration_path`, `manifest_path` and `files_root`. These are private immutable
original evidence paths outside all wallet directories. The loader rejects
links, traversal, missing/hash-changed files, extra declaration membership and
oversize/nonregular/public files. It reads no seed, private descriptor or key,
opens no Wallet and makes no RPC. The existing funding verifier independently
rejoins these raw originals to current active Core and actual member descriptors
on every source observation. Existing internal-transfer labels cannot bypass it.
New verified funding records still need their separately admitted original
journal entries; this profile neither imports them automatically nor treats
unrecorded capital as an opening zero or historical income.

The profile builder verifies configuration and original registration only. It emits
no event and creates no readiness, epoch, envelope, plan, budget or funds. The
ordinary CLI `observe`/`run` path installs the returned collector into the same
Engine. Each Engine collection retains its actual fresh nonce, original source
trace, complete member/liability/money checks and measured90-second deadline.
Existing Engine initialization markers and traces retain their original behavior
and grant no financial qualification. Collector admission also pins the profile
builder module and actual funding-reader module/configuration.
Recurring construction checks the recorded opening; it never reruns the
first-opening closure requirement against current live actions.

First opening remains an explicit separately authorized sequence: qualify the
actual source/tools/readers and member ownership; prepare a genuine opening with
the existing `build_collector`/`prepare_opening` APIs and original preserved
history; independently admit boundary/opening, envelope, funding plan and final
epoch using their existing APIs; then pin this profile. All missing original
roles, declarations, source hashes, funding ownership/journals or actual runtime
pins hold. The source builder never performs that financial transition.

56,970 and urgent40,000 model is **not selected or activated by this source**.
No figure is a default, renewed budget, available balance or permission to fund.
The old canary, all actions, liabilities, costs and permanent absences remain.
